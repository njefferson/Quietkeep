## 4. What the hub's sweep workflow takes from a caller

Read whole from `.github/workflows/branch-sweep.yml` in the hub:

- Triggers: `workflow_dispatch` and `workflow_call`. A caller uses `workflow_call`.
- One input, `delete`, a boolean defaulting to false. Off, the run only prints what it would
  remove. On, it deletes the removable branches.
- Top-level permissions are `contents: read`. The one job, `sweep`, declares `contents: write`,
  and the workflow's own comment says a called workflow can never hold more than its caller gave
  it, so the caller's job must grant `contents: write`.
- No secrets are passed. The deletion step uses the job's own token.
- It looks only at branches under `claude/*`, judges each against main by a merge-tree that must
  change nothing, and for a branch with no shared history compares the tree of its tip with the
  trees of main's history. Every other branch is printed as out of scope and untouched.
- Its own comment says a dispatched workflow must be on the repository's default branch, so the
  caller lives on main.

## 5. The caller for this repository

Pinned at the hub head by its full commit, passing the delete input through from its own dispatch
input with a false default, and granting the one scope the hub's workflow needs and nothing broader:

```
name: Branch sweep

# Calls the hub's branch sweep. A dry run unless `delete` is set. The sweep looks
# only at claude/* branches and removes one only when merging it into main changes
# nothing. A dispatched workflow must be on the default branch, so this file
# reaches main at the promote.

on:
  workflow_dispatch:
    inputs:
      delete:
        description: >-
          Delete the removable claude/* branches. Off, the run only prints what
          it would remove.
        type: boolean
        default: false

permissions:
  contents: read

jobs:
  sweep:
    permissions:
      contents: write
    uses: njefferson/noahjefferson/.github/workflows/branch-sweep.yml@9480bc607e890616ba30da55d8ef77e0c5031a37
    with:
      delete: ${{ inputs.delete }}
```

The repository's own pin check reads only lines that name `hub-gates.yml`, so this line is outside
its reach, while the hub's pin check and its local gates runner read every `uses:` line naming the
hub and require exactly one distinct pin. Step 25 therefore writes the same commit in both
workflows, and the hub's pin check run afterward proves it.

## 7. What the hook permits on main

`.branch-guard` declares work on staging and promote on main, with the escape variable
`QUIETKEEP_PROMOTE`. The generated hook exits 0 on staging, exits 0 on main only when that variable
is set, and refuses every other branch. The three repo-local checks (the accessibility receipt, the
branch state and the repository's pin check) run on every commit, promotes included. The caller
workflow therefore cannot be committed on main directly in this plan: a push to main deploys
production, and the commit would need the promote escape. It is committed on staging and reaches
main when the owner promotes.
